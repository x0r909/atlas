# Risk, Execution & Order-Path Security Checklist: Autonomous Crypto Trader

**Purpose**: Requirements-quality review of the decision→risk→order path: are the risk rules quantified, is the execution path's failure handling specified, and are the order-path security requirements verifiable? This checklist tests the requirements, not the implementation.

## Decision-to-Order Path Completeness

- [ ] CHK001 Is there an explicit functional requirement that the Execution Engine refuse any order not carrying a current approving verdict, or is that invariant only asserted after the fact in a success criterion? [Completeness, Gap, Spec §SC-001]
- [ ] CHK002 Is the validity window of an approving verdict defined (staleness/expiry), together with the required behaviour when an order arrives carrying an expired verdict? [Clarity, Gap, Spec §FR-021]
- [ ] CHK003 Is the authorization artifact between Risk Engine and Execution Engine (a signature or equivalent) stated as a requirement with an identified rule, or does it exist only in the plan's contract document? [Consistency, Spec §FR-021 vs plan contract]
- [ ] CHK004 Does the spec require that agent and model processes hold no venue credentials as a verifiable structural property, rather than only prohibiting the behaviour? [Measurability, Spec §FR-019]
- [ ] CHK005 Is every order-path mutation covered by the single-writer rule — place, modify, cancel, and stop replacement — and is the consequence of a non-Execution-Engine attempt specified (reject plus incident plus audit)? [Completeness, Spec §FR-019]

## Risk Rule Clarity and Measurability

- [ ] CHK006 Are the numeric trigger thresholds for each circuit breaker (volatility, spread, data staleness, clock drift) stated in the requirements, or do they exist only as defaults in the data model? [Ambiguity, Spec §FR-027]
- [ ] CHK007 Is "extreme volatility" and "spread wider than its threshold" quantified with both a reference measure and a lookback window, so two implementers derive the same trigger? [Ambiguity, Spec §FR-027]
- [ ] CHK008 Is the daily-loss window boundary defined — timezone, calendar day versus rolling 24 hours, and whether it resets on the venue's trading day? [Ambiguity, Spec §FR-024]
- [ ] CHK009 Is "maximum drawdown" defined precisely: peak of which equity series (closed, mark-to-market, portfolio-level), sampled at what interval, and inclusive of unrealised loss? [Ambiguity, Spec §FR-024]
- [ ] CHK010 Are the losses that feed the daily limit, drawdown, and cooldown defined net of fees, taxes, and slippage? [Clarity, Spec §FR-023]
- [ ] CHK011 Where expected costs enter sizing, is it specified whether the risk budget is gross or already reduced by the round-trip cost, so that the stated formula yields one size and not two? [Ambiguity, Spec §FR-023]
- [ ] CHK012 Are the values behind "maximum exposure per asset" and "maximum total exposure" stated as requirements, or left to unstated configuration defaults? [Gap, Spec §FR-024]
- [ ] CHK013 Is the loss-streak cooldown quantified (count and duration) and is its reset condition defined? [Ambiguity, Spec §FR-024]
- [ ] CHK014 Is the macro-event blackout specified with lead and lag windows in minutes plus an authoritative event source, rather than an unanchored "blackout window"? [Gap, Spec §FR-024]
- [ ] CHK015 Is the slippage guard's reference price defined (mid, last trade, or expected book-walk), so the configured limit is objectively testable? [Ambiguity, Spec §FR-032]
- [ ] CHK016 Is the unconfirmed-stop path bounded by an explicit timeout and retry count, instead of the open-ended "cannot be confirmed"? [Ambiguity, Spec §FR-033]
- [ ] CHK017 Is the reward-to-risk calculation specified formulaically — which costs, charged per side or round trip, and against which target and stop prices? [Ambiguity, Spec §FR-058]

## Cross-Requirement Consistency

- [ ] CHK018 Do the bracket-order requirement and the spot-only, no-derivatives requirement agree, given that the primary venue offers no native OCO — is client-side enforcement of the attached stop stated as the compliant interpretation? [Conflict, Spec §FR-030, §FR-050]

- [ ] CHK023 Is replay equality defined by the fields that must match, rather than by the phrase "the same verdict and order"? [Measurability, Spec §SC-007]

## Exception and Failure-Path Coverage

- [ ] CHK028 Are partial fills addressed: is the protective stop sized to the filled quantity, and is the handling of an unfilled remainder specified? [Coverage, Gap, Spec §FR-033]
- [ ] CHK029 Does the unknown-result order state have a terminal resolution requirement (query by client order id, bounded wait, incident, operator visibility), beyond the prohibition on resubmitting? [Coverage, Spec §FR-031]
- [ ] CHK030 Is behaviour specified when closing a position fails repeatedly, including the escalation and the state the system must reach? [Gap, Fail-safe, Spec §FR-033]
- [ ] CHK031 Is reconciliation mismatch expressed as a resolution workflow (who resolves, with what evidence, and what unblocks entries), not only as a block? [Coverage, Spec §FR-034]
- [ ] CHK032 Are venue rejection causes mapped to required behaviour (retry, abandon, halt) for the order path? [Gap, Spec §FR-030]
- [ ] CHK033 Is behaviour defined when the venue profile is missing, stale, or unverified — in particular, does trading block rather than proceed on assumptions? [Gap, Fail-safe, Spec §FR-036]

## Order-Path Security Requirements

- [ ] CHK034 Are credential scoping requirements quantified (trade-only, withdrawals disabled, IP whitelist) together with the required behaviour when the venue cannot report permissions? [Clarity, Spec §FR-036]
- [ ] CHK035 Is credential rotation or revocation specified as a requirement after a suspected compromise, with a maximum time to revoke? [Gap, Security]
- [ ] CHK036 Is "secrets never reach logs or the event bus" accompanied by a detectable violation signal, rather than standing as a prohibition alone? [Measurability, Spec §FR-040]
- [ ] CHK037 Is the isolation of untrusted external text from order-affecting state expressed as a testable invariant (labelled taint that cannot enter a proposal), beyond the general prohibition? [Measurability, Spec §FR-029]
- [ ] CHK038 Is the authentication strength for order-path operator actions (kill switch, mode change, risk configuration) specified as a requirement, including re-authentication for dangerous actions? [Coverage, Spec §FR-044, §FR-045]
- [ ] CHK039 Are replay-protection properties for operator commands (single-use confirmation, bounded validity window) stated as requirements? [Gap, Security]

## Dependencies and Assumptions

- [ ] CHK040 Are the venue facts the risk rules consume (minimum notional, step size, fees, taxes, rate limits) declared as verified-or-blocking, with a defined owner and a startup check? [Assumption, Spec §FR-036]
- [ ] CHK041 Is the tax treatment assumption (which side pays the final income tax, VAT status) documented as an assumption with an explicit invalidation path for recorded verdicts and backtests? [Assumption, Gap, Spec §FR-023]

## Notes

- Items are questions about what the requirements say (or fail to say); none of them asks for a test to be executed.
- Items marked with `[Gap]`, `[Ambiguity]`, or `[Conflict]` are the ones most likely to change implementation or acceptance tests if left unresolved.
- Highest-risk clusters if time is short: CHK001–CHK005 (order-path authorization), CHK006–CHK017 (threshold quantification), CHK028–CHK033 (failure paths).
- Mark items `[x]` only after review confirms the requirement-quality criterion is satisfied.
- Leave items unchecked when they still require clarification, correction, or reviewer evaluation.
- `/speckit.implement` reads checklist checkbox state as a gate and must not modify markers.
